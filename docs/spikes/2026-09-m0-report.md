### Findings

1. **Worker needs its file shipped.** Electrobun bundles only `build.bun.entrypoint` into `app/bun/index.js`. Bun's bundler neither emits nor rewrites `new Worker(new URL("./worker.ts", import.meta.url))`, so the worker first timed out in both builds. A standalone Bun 1.4.0 test showed the same `ModuleNotFound`, even with `worker.ts` passed as a second entrypoint, because the emitted file is `worker.js` while the reference stays `./worker.ts`. Fix used here: copy `src/bun/worker.ts` to `bun/worker.ts` and let Bun run the TS directly. That works only for self-contained workers. A worker that imports packages must be pre-bundled with `bun build` into a copied file.
2. **Copy sources must exist.** `hutch electrobun dev/build` fails with `CopySourceMissing` when a `build.copy` source is absent. `runner/` and `webview-probe/` hold placeholder READMEs until S3/S4 fill them.
3. **Packaged canary is a self-extractor.** `build/canary-macos-arm64/JSLab Spike-canary.app` is only a launcher plus `.tar.zst`. On first launch it extracts to `~/Library/Application Support/dev.jslab.spike/canary/`, installs an `uninstall` helper and manifest there, and replaces its own bundle with the real app. It then shows an installer window that waits for a click unless `ELECTROBUN_INSTALLER_UI_AUTOCLOSE=1` is set. Launched from this repo's external volume (`<volume>`), it stalled on a hidden macOS TCC prompt (`kTCCServiceSystemPolicyRemovableVolumes`). Launched from internal disk with auto-close, it ran unattended.
4. **`hutch pm exec` does not work with Bun delegation.** With `packageManager: "bun"`, `hutch pm exec -- vite build` forwards to `bun exec`, which fails with `bun: command not found: vite`. `hutch pm x --no-install vite build` works.
5. **Electrobun must be pinned.** Direct `hutch electrobun sync` floats on the stable channel (currently 2.0.1), so `hutch.config.ts` pins `electrobun: { version: "2.0.1" }`.
6. `tsc --noEmit` reports one error, inside the generated devkit (`WindowsUpdateTask.ts`: `AggregateError` is missing under the template's `lib: ES2020`). The spike sources themselves typecheck cleanly.

## S2

**Question:** Do Monaco's editor and TypeScript web workers load inside the packaged app's WKWebView over `views://`?

### Implementation

- Added `monaco-editor@0.56.0` to `spikes/s1-shell/package.json` via `hutch pm add monaco-editor@0.56.0`.
- Added `spikes/s1-shell/src/mainview/MonacoProbe.tsx`, rendered below the `<pre>` in `App.tsx`, matching the brief with one required import fix (see Deviations).
- Added `spikes/s1-shell/src/mainview/vite-env.d.ts` (`/// <reference types="vite/client" />`), not listed in the brief's file list, so `tsc --noEmit` recognizes Vite's `?worker` import suffix. Without it, `?worker` imports type-check as "Cannot find module" (TS2307) even though the Vite/Rollup build itself does not need the ambient type — this only mattered for a clean `tsc --noEmit`, not for the runtime pass criteria.

### Deviations from the brief

1. **`rpc` import path.** Per Task 1's finding (R2 ruling), `rpc` lives in `./rpc`, not `./App`. `MonacoProbe.tsx` imports `{ rpc } from "./rpc"` instead of `"./App"` as literally written in the brief.
2. **Worker subpath specifiers.** The brief's exact import paths, `monaco-editor/esm/vs/editor/editor.worker?worker` and `monaco-editor/esm/vs/languages/features/typescript/ts.worker?worker`, fail to resolve at Vite/Rollup build time (not just at runtime): `[vite]: Rollup failed to resolve import "monaco-editor/esm/vs/editor/editor.worker?worker"`. Root cause: `monaco-editor@0.56.0`'s `package.json` `exports` map is `"./*": "./esm/vs/*.js"` — the wildcard target already prepends `esm/vs/`. Requesting `monaco-editor/esm/vs/editor/editor.worker` matches the pattern with `* = "esm/vs/editor/editor.worker"`, and substituting into the target doubles the prefix to `./esm/vs/esm/vs/editor/editor.worker.js`, which does not exist (confirmed via `require.resolve` reproducing the identical doubled path and via inspecting `node_modules/monaco-editor/package.json`). Fix: drop the redundant `esm/vs/` prefix from the specifiers, giving `monaco-editor/editor/editor.worker?worker` and `monaco-editor/languages/features/typescript/ts.worker?worker`, which correctly resolve through the same `"./*"` pattern to `esm/vs/editor/editor.worker.js` and `esm/vs/languages/features/typescript/ts.worker.js`. This fix is exports-map plumbing, not the `?worker&inline` fallback described in the brief's Step 5 — the plain (non-inline) `?worker` variant passed once the specifiers were corrected, so Step 5's fallback was not needed.
3. `monaco.typescript.typescriptDefaults` / `monaco.typescript.getTypeScriptWorker()` as written in the brief were verified to be correct against the installed `monaco-editor@0.56.0` typings (a top-level `typescript` namespace re-exported from `esm/vs/index.d.ts`, distinct from the deprecated `monaco.languages.typescript` stub) — no change needed here, noted only because it looked suspicious before checking.

## S3

**Question:** Can the packaged app's main process spawn its bundled Bun binary as a child process with IPC, `NODE_PATH` package resolution, top-level await, disabled `.env` auto-loading, and `SIGKILL`, and should JSLab ship a separately pinned Bun binary for runners (risk R9)?

### Implementation

- `spikes/s1-shell/runner/child.mjs`: the IPC child script from the brief verbatim — sends `ready` with `Bun.version`/`process.execPath`, then on a `run` message resolves `fixture` from `NODE_PATH`, awaits a top-level `Promise.resolve(42)`, and reports `process.env.SPIKE_DOTENV` and `process.cwd()`.
- `spikes/s1-shell/runner/fixture-pkg/node_modules/fixture/{package.json,index.js}`: the fixture package resolved only via `NODE_PATH` (not a real dependency), verbatim from the brief.

- Step 5 (R9): downloaded Bun 1.3.13 darwin-aarch64, unzipped `bun-darwin-aarch64/bun` to `spikes/s1-shell/runner/bun-bin/bun`, added a second (then third) spawn in `s3Probe` using that path instead of `process.execPath`.

### Deviations from the brief

1. **Restructured `s3Probe` to run both binaries concurrently and share one spawn helper (`runBinary`)**, instead of the brief's single flat probe body. Rationale: Step 5 asks for "a second spawn... instead of process.execPath," and each spawn's own `await Bun.sleep(3000)` would serialize to 6s+ (then 9s once a third JSON-serialization run was added for diagnosis, see Deviation 3) if run sequentially, eating most of the verification window and slowing every rebuild/relaunch cycle. Field names differ from the brief's flat `out.readyMs`/`out.messages`/`out.exitCode`/`out.stderr`/`out.execPathCodesign`: they now live under `out.execPathRun.{readyMs,messages,exitCode,stderr,codesign}` and `out.pinnedBunRun.{...}` (same shape, one level deeper). All brief pass-criteria data is present, just at these paths.
2. **Removed `spikes/s1-shell/runner/README.txt`** (Task 1's placeholder) instead of keeping it, since `runner/` now holds real files and the copy rule no longer needs a placeholder to resolve.
3. **Added a third spawn, `pinnedBunJsonRun`**, not in the brief. The plain second spawn (`pinnedBunRun`, brief Step 5) crashed on the `run` IPC message with `TypeError: Unable to deserialize data.` — Bun's default "advanced" (V8 structured-clone) IPC serializer is not wire-compatible between the main process's Bun 1.4.0 and a separately pinned Bun 1.3.13 child. Per "when in over your head" — this is a genuine diagnostic follow-up, not scope creep — I re-ran the pinned binary with `Bun.spawn`'s `serialization: "json"` option to check whether an explicit stable wire format sidesteps the version-skew break. It did (see raw data). This finding materially changes the R9 answer, so it is included rather than left as an unexplained failure.
4. **`.gitignore` gotcha:** the existing blanket `node_modules/` rule in `spikes/s1-shell/.gitignore` also silently ignored `runner/fixture-pkg/node_modules/fixture/`, which the brief requires to be committed (git directory-exclusion means a nested `!pattern` cannot resurrect it). Rather than punch a hole in the blanket rule, the fixture files were `git add -f`'d directly; `.gitignore` itself only gained the new `runner/bun-bin/` entry (R3, the downloaded Bun 1.3.13 binary, ~60 MB, is not committed).

### Decision

**go:** M1's runner spawns the bundled Bun via `process.execPath` — same binary as the main process, same version, no separate download, no separate signing/notarization story, and no IPC-serialization coupling to worry about since both ends are always the same Bun build. This is `appPaths.runnerBootstrap()`'s answer for "which binary": `process.execPath`, not a bundled or pinned alternative.

**Copied-file path formula:** `join(PATHS.RESOURCES_FOLDER, "app", "runner", …)` — confirmed again here (`childPath`, `pinnedBunPath` both resolved and existed at this formula in the packaged canary), consistent with S1.

**R9 (separately pinned runner Bun): no, not for M0/M1.** A separately pinned Bun *can* work — it runs, and Hutch does not interfere with or re-sign it — but the default IPC wire format is not safe across Bun versions that differ from whatever `process.execPath` happens to be, and that gap only shows up at runtime (a silent-until-invoked child crash, not a build or launch failure). Shipping one would add ~63 MB, a separate download/update/notarization-verification story, and a standing requirement to always pass `serialization: "json"` on every runner IPC channel to stay safe against future version drift — for no capability `process.execPath` doesn't already provide at M0/M1's scope. Revisit only if a concrete feature gap appears between Electrobun's bundled Bun and a newer Bun release (e.g., a runner-only API JSLab needs before Electrobun catches up); if that happens, `serialization: "json"` is the required mitigation, not optional hardening.
