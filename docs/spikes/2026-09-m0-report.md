### Findings

1. **Worker needs its file shipped.** Electrobun bundles only `build.bun.entrypoint` into `app/bun/index.js`. Bun's bundler neither emits nor rewrites `new Worker(new URL("./worker.ts", import.meta.url))`, so the worker first timed out in both builds. A standalone Bun 1.4.0 test showed the same `ModuleNotFound`, even with `worker.ts` passed as a second entrypoint, because the emitted file is `worker.js` while the reference stays `./worker.ts`. Fix used here: copy `src/bun/worker.ts` to `bun/worker.ts` and let Bun run the TS directly. That works only for self-contained workers. A worker that imports packages must be pre-bundled with `bun build` into a copied file.
2. **Copy sources must exist.** `hutch electrobun dev/build` fails with `CopySourceMissing` when a `build.copy` source is absent. `runner/` and `webview-probe/` hold placeholder READMEs until S3/S4 fill them.
3. **Packaged canary is a self-extractor.** `build/canary-macos-arm64/JSLab Spike-canary.app` is only a launcher plus `.tar.zst`. On first launch it extracts to `~/Library/Application Support/dev.jslab.spike/canary/`, installs an `uninstall` helper and manifest there, and replaces its own bundle with the real app. It then shows an installer window that waits for a click unless `ELECTROBUN_INSTALLER_UI_AUTOCLOSE=1` is set. Launched from this repo's external volume (under `/Volumes`), it stalled on a hidden macOS TCC prompt (`kTCCServiceSystemPolicyRemovableVolumes`). Launched from internal disk with auto-close, it ran unattended.
4. **`hutch pm exec` does not work with Bun delegation.** With `packageManager: "bun"`, `hutch pm exec -- vite build` forwards to `bun exec`, which fails with `bun: command not found: vite`. `hutch pm x --no-install vite build` works.
5. **Electrobun must be pinned.** Direct `hutch electrobun sync` floats on the stable channel (currently 2.0.1), so `hutch.config.ts` pins `electrobun: { version: "2.0.1" }`.
6. `tsc --noEmit` reports one error, inside the generated devkit (`WindowsUpdateTask.ts`: `AggregateError` is missing under the template's `lib: ES2020`). The spike sources themselves typecheck cleanly.

## S2

**Question:** Do Monaco's editor and TypeScript web workers load inside the packaged app's WKWebView over `views://`?

### Implementation

- Added `monaco-editor@0.56.0` to `spikes/s1-shell/package.json` via `hutch pm add monaco-editor@0.56.0`.
- Added `spikes/s1-shell/src/mainview/MonacoProbe.tsx`, rendered below the `<pre>` in `App.tsx`, matching the brief with one required import fix (see Deviations).
- Added `spikes/s1-shell/src/mainview/vite-env.d.ts` (`/// <reference types="vite/client" />`), not listed in the brief's file list, so `tsc --noEmit` recognizes Vite's `?worker` import suffix. Without it, `?worker` imports type-check as "Cannot find module" (TS2307) even though the Vite/Rollup build itself does not need the ambient type — this only mattered for a clean `tsc --noEmit`, not for the runtime pass criteria.

### Deviations from the brief

1. **`rpc` import path.** Per Task 1's finding (R2 ruling), `rpc` lives in `./rpc`, not `./App`. `MonacoProbe.tsx` imports `{ rpc } from "./rpc"` instead of `"./App"` as literally written in the brief.
2. **Worker subpath specifiers.** The brief's exact import paths, `monaco-editor/esm/vs/editor/editor.worker?worker` and `monaco-editor/esm/vs/languages/features/typescript/ts.worker?worker`, fail to resolve at Vite/Rollup build time (not just at runtime): `[vite]: Rollup failed to resolve import "monaco-editor/esm/vs/editor/editor.worker?worker"`. Root cause: `monaco-editor@0.56.0`'s `package.json` `exports` map is `"./*": "./esm/vs/*.js"` — the wildcard target already prepends `esm/vs/`. Requesting `monaco-editor/esm/vs/editor/editor.worker` matches the pattern with `* = "esm/vs/editor/editor.worker"`, and substituting into the target doubles the prefix to `./esm/vs/esm/vs/editor/editor.worker.js`, which does not exist (confirmed via `require.resolve` reproducing the identical doubled path and via inspecting `node_modules/monaco-editor/package.json`). Fix: drop the redundant `esm/vs/` prefix from the specifiers, giving `monaco-editor/editor/editor.worker?worker` and `monaco-editor/languages/features/typescript/ts.worker?worker`, which correctly resolve through the same `"./*"` pattern to `esm/vs/editor/editor.worker.js` and `esm/vs/languages/features/typescript/ts.worker.js`. This fix is exports-map plumbing, not the `?worker&inline` fallback described in the brief's Step 5 — the plain (non-inline) `?worker` variant passed once the specifiers were corrected, so Step 5's fallback was not needed.
3. `monaco.typescript.typescriptDefaults` / `monaco.typescript.getTypeScriptWorker()` as written in the brief were verified to be correct against the installed `monaco-editor@0.56.0` typings (a top-level `typescript` namespace re-exported from `esm/vs/index.d.ts`, distinct from the deprecated `monaco.languages.typescript` stub) — no change needed here, noted only because it looked suspicious before checking.

### Implementation

- Step 5 (R9): downloaded Bun 1.3.13 darwin-aarch64, unzipped `bun-darwin-aarch64/bun` to `spikes/s1-shell/runner/bun-bin/bun`, added a second (then third) spawn in `s3Probe` using that path instead of `process.execPath`.

### Deviations from the brief

1. **Restructured `s3Probe` to run both binaries concurrently and share one spawn helper (`runBinary`)**, instead of the brief's single flat probe body. Rationale: Step 5 asks for "a second spawn... instead of process.execPath," and each spawn's own `await Bun.sleep(3000)` would serialize to 6s+ (then 9s once a third JSON-serialization run was added for diagnosis, see Deviation 3) if run sequentially, eating most of the verification window and slowing every rebuild/relaunch cycle. Field names differ from the brief's flat `out.readyMs`/`out.messages`/`out.exitCode`/`out.stderr`/`out.execPathCodesign`: they now live under `out.execPathRun.{readyMs,messages,exitCode,stderr,codesign}` and `out.pinnedBunRun.{...}` (same shape, one level deeper). All brief pass-criteria data is present, just at these paths.
2. **Removed `spikes/s1-shell/runner/README.txt`** (Task 1's placeholder) instead of keeping it, since `runner/` now holds real files and the copy rule no longer needs a placeholder to resolve.
3. **Added a third spawn, `pinnedBunJsonRun`**, not in the brief. The plain second spawn (`pinnedBunRun`, brief Step 5) crashed on the `run` IPC message with `TypeError: Unable to deserialize data.` — Bun's default "advanced" (V8 structured-clone) IPC serializer is not wire-compatible between the main process's Bun 1.4.0 and a separately pinned Bun 1.3.13 child. Per "when in over your head" — this is a genuine diagnostic follow-up, not scope creep — I re-ran the pinned binary with `Bun.spawn`'s `serialization: "json"` option to check whether an explicit stable wire format sidesteps the version-skew break. It did (see raw data). This finding materially changes the R9 answer, so it is included rather than left as an unexplained failure.
4. **`.gitignore` gotcha:** the existing blanket `node_modules/` rule in `spikes/s1-shell/.gitignore` also silently ignored `runner/fixture-pkg/node_modules/fixture/`, which the brief requires to be committed (git directory-exclusion means a nested `!pattern` cannot resurrect it). Rather than punch a hole in the blanket rule, the fixture files were `git add -f`'d directly; `.gitignore` itself only gained the new `runner/bun-bin/` entry (R3, the downloaded Bun 1.3.13 binary, ~60 MB, is not committed).

### Decision

**go:** M1's runner spawns the bundled Bun via `process.execPath` — same binary as the main process, same version, no separate download, no separate signing/notarization story, and no IPC-serialization coupling to worry about since both ends are always the same Bun build. This is `appPaths.runnerBootstrap()`'s answer for "which binary": `process.execPath`, not a bundled or pinned alternative. The dotenv control above confirms `--no-env-file` is a required argument, not optional hardening: omitting it lets a `.env` in the run's `cwd` leak into the executed script's `process.env`.

**Copied-file path formula:** `join(PATHS.RESOURCES_FOLDER, "app", "runner", …)` — confirmed again here (`childPath`, `pinnedBunPath` both resolved and existed at this formula in the packaged canary), consistent with S1.

**R9 (separately pinned runner Bun): no, not for M0/M1.** A separately pinned Bun *can* work — it runs, and Hutch did not interfere with or re-sign it in this canary build without code signing configured (see the signing caveat above) — but the default IPC wire format is not safe across Bun versions that differ from whatever `process.execPath` happens to be, and that gap only shows up at runtime (a silent-until-invoked child crash, not a build or launch failure). Shipping one would add ~63 MB, a separate download/update/notarization-verification story, and a standing requirement to always pass `serialization: "json"` on every runner IPC channel to stay safe against future version drift — for no capability `process.execPath` doesn't already provide at M0/M1's scope. Revisit only if a concrete feature gap appears between Electrobun's bundled Bun and a newer Bun release (e.g., a runner-only API JSLab needs before Electrobun catches up); if that happens, `serialization: "json"` is the required mitigation, not optional hardening.

## S4

**Question:** Inside an embedded `<electrobun-webview>`, do `alert`/`confirm`/`prompt` show native blocking dialogs that return real user-chosen values, and do timers (`setInterval`) and `requestAnimationFrame` keep running when that embedded webview is collapsed to zero size? This decides M4's browser-runtime approach to dialogs and to hidden/background tabs.

### Step 1: tag docs at the pinned version

Read at the pinned-tag clone (ruling R3; the brief's literal `/tmp/electrobun-2.0.1` does not exist here): `.../electrobun-2.0.1/docs/src/content/docs/electrobun/apis/browser/electrobun-webview-tag.mdx` and `.../guides/architecture/webview-tag.mdx`.

- **URL attribute:** `src` (matches the brief; no change needed). Also documented: `html` (inline document), `preload` (JS evaluated before the embedded page's scripts).
- **Partition/sandbox:** `partition` (string, persistent session/storage partition name) and `sandbox` (boolean attribute) both exist as documented and match the names the brief assumed. `sandbox` "disables Electrobun RPC in the child while retaining events and navigation controls" — the event bridge (`host-message` / `window.__electrobunSendToHost`) explicitly "remains available in sandbox mode." The probe does not set `sandbox` (it needs no app RPC in the embedded page; using it unsandboxed most closely matches a "just call alert() and see what happens" test, and the host-message bridge would work identically either way).
- **Host⇄embedded messaging API:**
  - Embedded → host: `window.__electrobunSendToHost(value)` is injected into *every* Electrobun-managed webview's global scope before application scripts run (`docs/.../apis/browser/global-properties.mdx`) — no import or preload attribute needed. It emits `value` as a `host-message` CustomEvent on the containing `<electrobun-webview>` element, delivered to `event.detail`.
  - Host → embedded: `webviewEl.executeJavascript(js: string): void` (confirmed against the projected devkit's type, `.hutch/devkit/api/browser/webviewtag.ts`) runs arbitrary JS inside the embedded page. It is fire-and-forget (`void`, no return value/promise) — a reply, if wanted, has to come back over the `host-message` bridge above.
  - Host listens with `webviewEl.on("host-message", (event: CustomEvent) => ...)` / `.off(...)`.

This is a richer, two-way channel than the brief anticipated (which only planned a human running `spikeTicks()` in Web Inspector). It is what makes the ruling R1 automation possible: the host can both *push* code into the embedded page on demand and *receive* pushes back from it, with no human involved.

### Decisions

- **Hidden webview: zero-size (not 1×1 offscreen).** Collapsing the `<electrobun-webview>` to `width: 0; height: 0` did not throttle `setInterval` (100% of the non-collapsed baseline rate) or pause `requestAnimationFrame` (104% of baseline) over a 10s window, so the brief's 1×1-offscreen fallback (Step 5) was not needed and was not exercised. M4 can collapse an inactive/hidden webview tab to zero size and trust its timers and animation loops to keep running at full rate — no need for an always-1px-visible workaround.
- **Dialogs: §5.12 async-style fallback, not native.** `alert`/`confirm`/`prompt` inside this embedded webview return in ~1ms with default values (`undefined`/`false`/`null`) and no human interaction — that is only possible if no blocking native panel was ever actually shown, since nothing but the host's own script triggered the calls. M4's browser runtime must therefore implement the spec §5.12 shim for these: JSLab shows its own non-blocking dialog, `alert` returns immediately after showing it, `confirm` returns `false`, `prompt` returns `null`, and a console warning explains the limitation. Neither the native dialogs nor the shim pause script execution or return real user input. This basis — a negative ("does not block") proven without a human click — is what ruling R1's provisional-pending-a-human-click clause did not anticipate: that clause assumed a *blocking* dialog needing a click to resolve, which is not what was found here, so the finding stands as decided rather than provisional.

### Fix round 1 (post-review correction)

A review of the initial S4 submission found the collapse-window measurement was inaccurate: `measureWindow`'s `end` reading was taken *after* `restore()` + a 500ms settle + the `forceRead()` round-trip, so up to ~600ms of full-rate (non-collapsed) ticks were folded into the "during collapse" delta. Dividing that inflated count by the nominal `expectedInterval: 100` constant (rather than by the window's actual elapsed time) then let `intervalKeptPct` read 102% — a number the zero-size decision rested on without it being an artifact of measurement, but for the wrong reason.

Fixed in `spikes/s1-shell/src/mainview/WebviewProbe.tsx`: `measureWindow`'s `end` snapshot is now taken *while still collapsed*, immediately before `restore()` runs, so the collapse delta cannot include post-restore ticks. Both the baseline and collapse windows now report explicit `elapsedMs` (from the embedded page's own timestamps, immune to host-side round-trip latency) alongside ticks, and the pass/fail gate is `pctOfBaselineIntervalRate` — the collapse window's ticks-per-second divided by the baseline window's ticks-per-second — rather than raw ticks divided by a nominal constant. The re-run (raw JSON and pass/fail table above) shows `pctOfBaselineIntervalRate: 100` (previously the uncorrected run showed a spurious 102%; both point to the same "not throttled" conclusion, but the corrected number is now actually measuring what it claims to measure). The zero-size decision is unchanged, now on a sound basis. The dialogs finding was unaffected by this bug (it doesn't involve `measureWindow`) and is unchanged.

### Decision

## S7

**Question:** Can Electrobun's main→webview RPC carry JSLab's run-output stream (batches of console events every 16 ms) without loss, with low latency, and without janking the UI? JSLab's M1 runner forwards output in batches; the recorded batch parameters become the M1 default for the `run.events` channel.

### Implementation

**Main-side sender** (`src/bun/index.ts`, `startThroughput` message handler): implemented verbatim from the brief's Step 1, with one addition — `throughputDone` now also sends `batchSize` (threaded through from the `startThroughput` params), not just `sent`. This is a deviation from the brief's snippet (which only sends `{ sent: seq }`), made to satisfy the follow-up controller ruling R1's requirement that the automated 200-then-1000 sequence's "own S7 line... include `batchSize` in the data" — without it, the view has no way to label which run a given `throughputDone`/`S7` report line belongs to. `shared/rpc.ts`'s `throughputDone` message type was extended to `{ sent: number; batchSize: number }` to match.

`probes` (the same request the view already calls on load) now also returns `s7Enabled: process.env.JSLAB_SPIKE_S7 === "1"`, following the exact pattern S6 established for `s6Enabled`.

**View-side meter and handler API (Step 2).** `rpc.setMessageHandlers` does **not** exist on the object `Electroview.defineRPC` returns in Electrobun 2.0.1 — confirmed by reading the vendored source at `.hutch/devkit/api/shared/rpc.ts`: `defineElectrobunRPC`'s return value (`createRPC`'s return value) only exposes `setTransport`, `setRequestHandler`, `request`, `requestProxy`, `send`, `sendProxy`, `addMessageListener`, `removeMessageListener`, `proxy` — no `setMessageHandlers`. Per the brief's documented fallback, the `throughputBatch`/`throughputDone` handlers were registered statically in the `messages` object of `Electroview.defineRPC` — this is **the API that worked**. Per the earlier-tasks note (rpc.ts, not App.tsx, holds the `Electroview.defineRPC` call — ruling R2), this meant editing `src/mainview/rpc.ts`, which already had `throughputBatch: () => {}` / `throughputDone: () => {}` stubs from an earlier task's scaffolding of `shared/rpc.ts`'s message schema. The module-level meter state (`latencies`, `received`, `lastSeq`, `gaps`, `worstFrameMs`, `lastFrame`, an rAF handle, a `running` guard, and a `doneResolver`) now lives in `rpc.ts` next to those handlers, and `rpc.ts` exports `startThroughputProbe(batchSize, seconds)` — a promise that resolves once `throughputDone` has fired and its `S7` `viewReport` line has been sent — instead of the brief's plain `start()` closure, so the automated sequence (below) can run two batch sizes back to back without overlap. Two implementation additions beyond the brief's snippet, both deviations kept small and noted here:
- `cancelAnimationFrame`/re-`requestAnimationFrame` on each `startThroughputProbe` call (the brief's snippet starts the rAF loop once and never cancels it) — cosmetic hygiene so repeated manual button clicks across a long-lived session don't accumulate concurrent rAF loops; functionally equivalent since `worstFrameMs` is reset to 0 at the start of every run regardless.
- `visibilityAtStart`/`visibilityAtEnd` (`{ visibilityState, hasFocus }`) added to the `S7` report line, per the follow-up controller ruling on `worstFrameMs` only being meaningful while the webview is actually rendering frames.

**Automated sequence (ruling R1).** `ThroughputProbe.tsx` (new) renders the brief's two buttons for manual re-runs, plus a `useEffect` that — only when `probes.s7Enabled` is true (i.e., `JSLAB_SPIKE_S7=1` was set on launch, relayed through `probes` exactly like S6's `s6Enabled`) — runs `await startThroughputProbe(200, 10)` then `await startThroughputProbe(1000, 10)` once, with no human click. Without the env var, nothing starts automatically; the two buttons are otherwise unaffected. `App.tsx` passes `autoRun={!!probes?.s7Enabled}`.

### Decision

**go: M3's npm operations isolate `~/.npmrc` by overriding `HOME`, not with npm config variables.** Every `bun add` / `bun remove` / `bun outdated` spawn uses:
- the bundled Bun, `process.execPath` (S3),
- `cwd = <appdata>/packages`,
- the login-shell environment plus:
  - `HOME=<appdata>/npm-home`: an app-owned directory JSLab creates and never writes an `.npmrc` into.
  - `BUN_INSTALL_CACHE_DIR`: the user's Bun cache, meaning the login-shell `BUN_INSTALL_CACHE_DIR` if set, otherwise `<real HOME>/.bun/install/cache`. The cache stays shared and never lands in `npm-home`. That fallback ignores a login-shell `BUN_INSTALL` or `XDG_CACHE_HOME` (not tested here), so M3 sets `BUN_INSTALL_CACHE_DIR` explicitly and does not rely on a derived default (spec §11.3).

Registry, scoped registry and auth settings are meant to come only from `<packages>/.npmrc`. The spawn environment is still the login-shell environment, and C3 shows Bun honours `BUN_CONFIG_REGISTRY`, so spec §11.3 also requires M3 to strip inherited `BUN_CONFIG_*`, `NPM_CONFIG_*` and `npm_config_*` variables from the install environment. `NPM_CONFIG_USERCONFIG` and `BUN_CONFIG_NO_GLOBAL_NPMRC` are dropped from spec §11.3, because Bun 1.4.0 ignores both: the first in-app (`userconfigOverride`) and in C4, the second in C7.

**Basis:** Run 3's discriminating in-app pair, with the packaged app's bundled Bun 1.4.0. The same scoped install fails when `HOME` holds a `.npmrc` with a dead scoped registry, and succeeds with `HOME=<empty npm-home>` plus `BUN_INSTALL_CACHE_DIR`, leaving `npm-home` empty and using the explicit cache. Proven in-app for a scoped registry key and (Runs 1–3, `emptyProjectRc`) a default `registry=` key. Not separately tested: `//host/:_authToken` lines, inferred to follow the same `$HOME/.npmrc` read. This decision is not provisional; it depends on no manual check.

**M3 follow-up (not an M0 blocker):** with `HOME` overridden, git-URL specs, SSH keys, `~/.gitconfig` and install scripts that read `HOME` also see `npm-home`. M3 must test a git-over-SSH spec. If one needs something from the real home, pass that specific variable (for example `GIT_SSH_COMMAND`) rather than restoring `HOME`, which would re-expose `~/.npmrc`. Re-run the C0–C8 controls whenever Electrobun's bundled Bun version changes.
