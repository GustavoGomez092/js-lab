# JSLab ↔ RunJS 4.1.0 Feature Parity Checklist

This is the v1 release gate (spec §22.4). Every row must be ✅ (implemented and verified) or 📝 (approved documented deviation) before 1.0 ships.

**Clean-room note:** the RunJS column uses only public sources:
- **Docs:** runjs.app documentation pages
- **CL x.y:** CHANGELOG / GitHub release notes
- **#n:** GitHub issue or discussion
- **Strings:** the public `translations/en/translation.json` in `lukehaas/RunJS`

JSLab behavior and defaults are defined in the spec ([`2026-09-12-jslab-design.md`](superpowers/specs/2026-09-12-jslab-design.md)).

**Verify column:**
- **U:** unit
- **I:** integration
- **E:** E2E scenario
- **M:** manual QA

**Status:** ⬜ not started · 🚧 in progress · ✅ done · 📝 deviation (see the notes)

## Deviation notes

- **EX-16:** logpoint-triggered runs report `reason: "auto"`; spec Appendix A sketches a `"logpoint"` reason. The shipped `runStartParamsSchema` accepts `"auto" | "manual"` only, and Main refuses exactly `reason === "auto"` while Safe Mode is active (spec §5.14). A separate `"logpoint"` reason would be a run reason Safe Mode does not refuse, so a logpoint change arms Auto Run and goes out as an automatic run. No user-visible difference.
- **EX-22 / D2:** RunJS's "Node.js" runtime is replaced by Bun (Node-compatible). Known differences are documented in `docs/user/bun-vs-node.md` (spec §26). In "Browser & Node APIs", synchronous `fs`/`child_process` APIs aren't available; errors explain this and offer to switch the tab to Bun.
- **EX-22 / D13:** RunJS opens new tabs in its Browser & Node.js environment; JSLab opens them in **Bun**. Decided in M4: with the browser runtimes registered, a default tab routed to a webview that began evaluating and never reported a result, and a default that can't finish what it starts is worse than the Bun fallback it replaced. `run.defaultRuntime` lets a user choose otherwise. Revisit when web runs settle reliably.
- **EX-26:** `process.memoryUsage()` works in `bun` only. `browser-node`'s `process` is a page-load snapshot and doesn't implement it.
- **EX-34:** the `browser` runtime enforces CORS, as a real browser does. `browser-node` and `bun` don't.
- **EX-37:** "Show Transpiled Output" is a **side-bar panel**, not a separate tab kind. Spec §7.4 calls it a "read-only side tab"; JSLab's side region is the side bar, with a panel switch (§7.1). The panel is read-only, refreshes on each run, carries the instrumentation toggle, and says when the buffer has moved on since the output was produced — everything §7.4 requires of it.
- **EX-37:** "Hide instrumentation" **re-transforms** rather than stripping calls. The toggle returns the same source transformed again with Auto Log, logpoints and loop protection off, which is exact; pattern-stripping `__jl` calls out of generated output is not.
- **LB-06:** two divergences from a Bun run, both accepted in M4 and recorded in `docs/qa/m4-checklist.md`: `import * as ns` over a bundled package can enumerate the default export's own keys (values are identical; only `Object.keys(ns)` differs), and `stream`, `events` and `buffer` each carry their own copy of their dependencies, so `instanceof` across those modules can be `false`.
- **WV-06:** tile arrangement was never built in M4, and R-WEBVIEW-TAB-1 has since retired it entirely — there is no arrangement left to store or drag. M4 shipped the Web View **toggle** (⌥⌘W, View → Web View, status bar), which remains the only way to control the tile.
- **OU-07:** user-defined getters are evaluated only when expanded, to avoid side effects during logging.
- **TF-11:** the webview doesn't get a dropped item's path on Electrobun 2.0.1 (R-M3-SPIKE-1). A dropped file opens as an unsaved scratch copy titled with the file's name; a dropped folder shows a notice pointing at Actions → Set Working Directory…. Revisit when Electrobun adds native drop paths.
- **TF-21:** closing the last tab keeps the app open with a fresh tab. ⌘W on a **lone untouched** tab still closes the window. M5a changed what "untouched" means: the guard used to test `code === ""`, which the welcome tab (38 lines of sample) silently broke, so a first-run user's ⌘W closed the tab and left an empty window. It now tests a `pristine` flag, cleared by content comparison in Main and on the first edit in the UI.
- **ST-08:** `WELCOME_TITLE` (`apps/desktop/src/main/welcome.ts`) is a user-visible Main string living **outside** `apps/desktop/src/main/strings.ts`, which declares itself the home for exactly those. It has to move in the §17 i18n extraction sweep, along with `WELCOME_CODE`'s prose.
- **ST-12:** the welcome tab's `fetch` and React samples **ship commented**. They demonstrate both APIs without a first Run making a network request, or needing a runtime switch to avoid an error; uncommenting either line is the demonstration.
- **ST-12:** the **E2E harness suppresses the welcome tab by default**. Every harness launch gets a brand-new data folder, so every one of them is a genuinely first launch, and the sample would rewrite the first tab that most scenarios assume. `apps/desktop/src/main/main-services.ts` therefore passes `firstRun` only when `JSLAB_E2E !== "1"` or `JSLAB_E2E_WELCOME === "1"`, and the scenarios that are *about* the welcome tab opt back in by name. The knob is harness-only: a shipping launch sets neither variable and always gets the welcome tab.
- **ST-12:** known limitation — a **first launch never writes `session.json`** until something flushes it (the write fires only for recovered or repaired sessions). A crash before the first flush makes the next launch a first run again and orphans the welcome buffer. This is a pre-existing property of every `createTab()`, not new in M5a: buffers are written synchronously, `session.json` only on a debounced flush. No data is destroyed; the orphaned buffer file stays on disk, merely unreferenced.
- **PL-02:** Windows and Linux follow v1.
- **PL-05:** there's no licensing; JSLab is MIT and fully free.
- **PL-06:** no deep links in v1, for security (RunJS #500).
- **TL-12 / §7.5:** the Snippets panel lives in the **side bar**, and ⌘B opens it there rather than in a modal. Spec §7.5 offers "Side bar panel (or modal when the side bar is hidden)"; JSLab's side region is the side bar with a panel switch (§7.1), so ⌘B shows the side bar on the Snippets panel when it is hidden, switches to it when another panel is showing, and hides the side bar when Snippets is already showing. `view.sideBar` keeps exactly one writer — the `view.toggleSideBar` command — so the key and the activity-bar click cannot diverge.
- **TL-16 / §13.3:** snippet autocomplete **expands on Tab** and only lists when it is genuinely useful. §13.3 requires a snippet to be suggested even after its full name is typed (RunJS #488). JSLab satisfies that but does not copy VS Code's continuous fuzzy suggest, whose exact-match ranking is an open complaint (VS Code #244170, #66621): typing a full name and pressing Tab expands it outright, and the suggest list collapses to the single exact match instead of continuing to rank longer siblings alongside it. Tab is left untouched when there is no trigger word before the caret, so the keystroke still reaches Monaco and indents.
- **TL-13 / §13.1:** deleting a snippet is **confirmed and then undoable**. §13.1's confirmation ships verbatim (`Delete snippet "<name>"?`); the panel additionally keeps the deleted record and offers Undo until the next change, so a destructive action on a cheap, easily recreated artifact is recoverable rather than merely deliberate.
- **TL-17 / §13.4:** an imported snippet is **always given a fresh id**. The `jslab-snippets` format carries ids, but a file JSLab did not write is untrusted, so merging matches on name (case-insensitively) and mints a new id for everything it adds; an overwrite keeps the *existing* record's id and `createdAt`. An imported file can therefore never alias or overwrite an existing record by claiming its id.
- **TL-17:** known limitation — **exporting before the Snippets panel has ever been opened writes an empty library.** `snippets.export` sends the UI store's snippet array, and the only thing that fills it is the panel's own mount effect (`apps/ui/src/snippets/SnippetsPanel.tsx`, the single caller of `snippets.list`). The command opens the panel first, but reads the array in the same turn, before the mount effect has run. Choosing Snippets ▸ Export from the menu in a session where the panel was never shown therefore writes `{"format":"jslab-snippets","version":1,"snippets":[]}` over the chosen file. Exporting from the panel's own Export button is unaffected, and so is any export after the panel has been opened once. Not fixed in M5b: the fix is for Main to export from its own store rather than from a UI-supplied array.
- **TL-17:** a first-ever **import can in principle be answered before anything is listening.** `snippets.import` deliberately opens the panel before asking Main for the dialog, because `snippets.imported` is only heard by a mounted panel, but the listener registers in that panel's mount effect — so a Main reply arriving before the effect runs is dropped silently. In practice the reply cannot land before the user has picked a file, which is many frames later; the ordering is recorded rather than relied upon.
- **TL-13 / §13.2:** inserted snippet text is **live code**. Insert arms Auto Run, so with Auto Run on, an inserted snippet — including one that came from an imported library — executes like anything else typed into the editor. This is user-initiated in every case (the user chooses the snippet and the insert), but an imported library is untrusted content, and inserting from one is the moment it becomes runnable.
