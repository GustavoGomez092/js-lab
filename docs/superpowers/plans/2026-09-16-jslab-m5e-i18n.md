# JSLab M5e — Internationalization Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put every user-visible string in JSLab behind a namespaced key looked up at runtime, ship `en` complete and four seeded locales, and make a missing, stale or unused key fail CI loudly.

**Architecture:** The UI already routes essentially all of its copy through two central modules (`apps/ui/src/strings.ts`, `apps/desktop/src/main/strings.ts`), so this milestone is not a hunt through components — it is (a) a *mechanism* that resolves a locale, loads JSON, and checks keys, and (b) a one-time *sweep* that converts those two modules plus the shared command titles and the native menu labels into `t()` calls. The locale is fixed for the life of a window: Main resolves it from `app.uiLanguage`, appends `?lng=<lng>` to both view URLs, and each React tree initializes i18next synchronously from that query parameter — which is exactly what the spec's "changing the language needs a restart" buys us, and why no live re-render plumbing, and therefore no `react-i18next`, is needed.

**Tech Stack:** Bun 1.4.0 (bundled) / 1.3.13 (local), Electrobun 2.0.1 via Hutch 0.24.3, React 19, Vite 8, TypeScript 7, Zustand, zod 4, Biome 2.5.13, i18next (new, exact pin, MIT).

**Spec:** docs/superpowers/specs/2026-09-12-jslab-design.md

### 3. The JSX-literal rule can be turned on today, clean

Two searches over every `.tsx` under `apps/ui/src`, each with a control:

- JSX text children matching `>[A-Za-z][A-Za-z ,.!?'-]{2,}<` — **2 hits, both false positives** (`ExpandHandle` and `CreateTextEditor` type aliases, where the `>` and `<` are generics/arrows, not JSX). Control: the same file set matches `<` 35 times in `StatusBar.tsx` alone, so the pattern reaches the files.
- Literal `aria-label="…"`, `title="…"`, `placeholder="…"`, `alt="…"` attributes — **0 hits** across all 28 `.tsx` files.

Every label in the UI already reads `strings.…`. That is the single most important survey result: **the sweep is not a component-by-component retrofit**, and the lint rule has nothing to fix before it can be enabled.

### 4. Biome *can* express the rule — natively, with no plugin

`biome.json` pins `@biomejs/biome` `2.5.13` with `"linter": { "rules": { "preset": "recommended" } }` and no `plugins` key.

- Biome 2.5 ships a built-in rule **`style/noJsxLiterals`** (added in 2.2.4, documented as "Same as `react/jsx-no-literals`"). It is not in `recommended`, so it must be enabled explicitly. Its `noStrings: true` option extends it from JSX text children to **string literals in JSX attributes and expressions**, which is the whole surface §17 asks for. `allowedStrings` provides an allowlist.
- Biome 2.5 *also* supports user-authored GritQL plugins via a top-level `"plugins": ["./x.grit"]`, with `register_diagnostic(span, message, severity, fix_kind)`. **We do not need one**, and this plan deliberately does not use one: the GritQL reference states plainly that "some features are still outright missing", its documented JSX examples cover attributes but not text children, and it warns that CST node names "can change between versions". A built-in rule is the cheaper and more durable choice.
- **What `noJsxLiterals` cannot see:** a hard-coded string that never appears in JSX — `store.setStatusMessage("Saved")`, a `label:` field in `menu.ts`, a `title:` in `COMMANDS`. Three of our six surfaces are exactly that shape. So the lint rule is necessary but not sufficient, and Task 7 pairs it with a key-check that catches drift in both directions, plus Task 11 adds a syntactic scan of the `label:`/`text:`/`title:` positions with an exact expected count of zero.

### 5. Preferences already persist the locale — no schema change needed

`packages/shared/src/settings.ts:33` already has `export const UI_LANGUAGES = ["system", "en", "es", "ja", "zh", "pt"] as const;` and line 72 `app: section({ uiLanguage: choice(UI_LANGUAGES, "system") })`, at `SETTINGS_VERSION = 3`. `apps/ui/src/settings/fields.ts:40` already renders it on the General tab with `restart: true`, and `apps/ui/src/strings.ts:534` already carries the option labels `{ system: "System", en: "English", es: "Español", ja: "日本語", zh: "中文", pt: "Português" }`.

M2 shipped the setting and the UI for it; **nothing was ever wired to it**. `git grep -n uiLanguage` finds no reader outside the schema, the field definition, and the label map. So M5e adds no settings migration and no new zod schema — it adds the consumer. The one copy change needed is the field's help text, which still reads "More languages arrive in a later version."

Persistence path: `SettingsStore` (`apps/desktop/src/main/services/settings-store.ts`) → atomic write of `<userData>/settings.json` with a `.bak`, debounced, with a 10 s write timeout.

### 6. How the E2E harness drives the app

`packages/e2e/src/app.ts` exposes `launchApp(options)` which, critically for this milestone:

- **writes `settings.json` before the app starts** — `if (options.settings) await writeFile(join(userData, "settings.json"), JSON.stringify(options.settings))`. A locale is therefore in force from the first frame, exactly as a real restart would give it.
- exposes `relaunch(next)` → `launchApp({ ...next, channel, userData })`, reusing the same data folder. This is how a restart is tested.
- exposes `state()` returning `{ ui, main }`, where **`main.menu` is the built native menu** — `packages/e2e/scenarios/menu.test.ts` already asserts `find(await menuOf(app), "Run")?.label === "Run    ⌘R"`. Localized menu labels are therefore assertable end-to-end with no new harness plumbing.
- exposes `settingsState()` / `settingsCommand(id, args)`, routed with `window: "settings"` to the Settings window's own agent (`apps/ui/src/settings/settings-agent.ts`), which accepts `settings.set`, `settings.tab`, `settings.resetAll`, `npmrc.*`.

### 7. Packaging: how Main can read "the same files"

Main is compiled from `src/main/index.ts` and imports **no JSON today** (`git grep -E 'from "[^"]*\.json"'` over `apps/desktop/src`, `apps/ui/src`, `packages` → no matches; control: `index.ts` has 39 relative imports). `apps/desktop` does not depend on `@jslab/ui`, so it cannot import across that boundary.

The repo already solved this exact problem once, for `THIRD-PARTY-NOTICES.md`: `hutch.config.ts`'s `build:bundles` stages the file into `dist/`, and `electrobun.config.ts` copies `"dist/THIRD-PARTY-NOTICES.md": "THIRD-PARTY-NOTICES.md"` with a project-relative key, because that config block rejects `..` components. This plan follows that precedent exactly — stage `apps/ui/src/i18n/locales/` into `dist/locales/`, copy it to `Resources/app/locales/`, and give `app-paths.ts` a `localesDir` with a `JSLAB_LOCALES_DIR` override, matching the existing `runnerBootstrap` / `webRunnerBootstrap` / `transformWorker` idiom. Main then genuinely *reads the same files* at runtime, and stays free of a bundler-inlined copy that could drift.

The UI takes the other route: Vite bundles the five JSON files into the view. This is forced by the CSP — `connect-src 'self' views: ws://127.0.0.1:* ws://localhost:*` permits no runtime fetch of a locale.

### 8. CJK and layout — what actually breaks

Two distinct problems, in opposite directions.

**a. `es` and `pt` overflow; `ja` and `zh` change metrics.** Spanish and Portuguese UI copy typically runs 15–30 % longer than English. Japanese and Chinese use fewer characters but each is full-width (~2× the advance of a Latin character) and neither language breaks on spaces. The Graphite chrome has real fixed constraints (`apps/ui/src/styles.css`): `--activity-width: 48px`, tab labels at `max-width: 220px` with `text-overflow: ellipsis`, the side bar at `width: 280px; min-width: 240px`, status-bar items in a `white-space: nowrap` row, and the settings field grid.

**b. None of the six bundled fonts has a CJK glyph.** `apps/ui/src/themes/fonts.ts` builds the stack as:

```ts
export function fontStack(name: string): string {
  return `"${fontFamily(name).replaceAll('"', "")}", ui-monospace, Menlo, monospace`;
}
```

JetBrains Mono, Fira Code, DejaVu Sans Mono, Hack, Ubuntu Mono and Source Code Pro all lack CJK coverage, and so do `ui-monospace` and `Menlo`. Under `ja`/`zh`, every CJK run in the chrome falls through the entire stack to last-resort substitution, landing on Hiragino Sans or PingFang SC with different metrics and a taller line box than the stack was tuned for. This is a real defect the milestone must fix, not a cosmetic worry — Task 13 appends explicit CJK families to the stack and Task 14 gates label widths.

**What can and cannot be tested automatically.** The unit suite runs under happy-dom, which has **no layout engine** — `getBoundingClientRect()` returns zeros and text is never measured. So a test that claims "the label fits" would be a lie. Task 14 instead ships an honest proxy: a deterministic **display-width budget** (East-Asian full-width and wide characters count 2 columns, everything else 1) asserted per width-critical key, with budgets derived from the measured CSS. It is a proxy and the plan labels it as one; the real check is the `ja`/`es` screenshot pair in the manual QA checklist (Task 15).

## The sequencing decision

**Recommendation: split M5e in three and land the mechanism first, the sweep last.**

> **In one sentence:** the mechanism touches no file the sibling milestones edit, so it can land now and make their own "no hard-coded strings" rule machine-checked; the extraction sweep rewrites the one file all three of them append to, so it must land last and be done once, over the final string set.

### Why not "extract first"

If the sweep lands first, `apps/ui/src/strings.ts` stops being a tree of literals and becomes a tree of `t()` calls. M5a's Task 5 says "Add to `apps/ui/src/strings.ts`, immediately after the `install` group" and then shows a literal block; M5b's Task shows "add a `snippets` block after the `env` block"; M5d's says `settings.keybindings` gets `conflict: (titles: string) => \`Also bound to ${titles}\``. Those are **25 named insertion points across three committed plans, written against a form that would no longer exist.** Every one would need rewriting, and the strings they add would then have to be extracted a second time anyway. That is the worst of both orders.

### Why not "lint rule first, everything else after"

This is closer, and it is half of what I recommend — but the rule alone is not the expensive part. The costly, collision-prone part is the shape of `strings.ts`, and the rule does not change that shape at all.

### What I actually recommend, and why it is safe

**Phase A (Tasks 1–7) lands immediately, before or alongside M5a/M5b/M5d.** It touches: `packages/shared/src/locale.ts` (new), `apps/desktop/src/main/main-view-url.ts`, `apps/desktop/src/main/app-paths.ts`, `apps/desktop/src/main/i18n.ts` (new), `apps/ui/src/i18n/**` (new), `hutch.config.ts`, `electrobun.config.ts`, `biome.json`, `.github/workflows/ci.yml`, `docs/user/translating.md` (new).

It touches **none** of `apps/ui/src/strings.ts`, `apps/desktop/src/main/strings.ts`, `packages/shared/src/commands.ts`, `apps/desktop/src/main/menu.ts`, or any component. Cross-checked against all three sibling plans' file lists: the only overlap is `apps/desktop/src/main/menu.ts` and `packages/shared/src/commands.ts`, which M5d edits and **Phase A does not**. So Phase A invalidates nothing, and its `noJsxLiterals` rule *enforces* the rule the sibling plans already told their implementers to follow — turning a written instruction into a CI failure, at the exact moment three milestones are about to add hundreds of strings.

**Phase B (Tasks 8–11) must wait for all three to merge.** It is the sweep. Waiting means it runs once over the final string set — M5a's logpoint and transpiled-output copy, M5b's snippets panel, M5d's keybindings pane included — instead of running now and again later.

**Phase C (Tasks 12–15) follows Phase B**, because seeded locales, width budgets and the restart notice all need real keys to point at.

### The one cross-milestone obligation, and how it is enforced

After Phase B, `en.json` is generated from the swept sources and committed. If a *later* change adds a string without regenerating, the key check fails with `unknownKeys` naming the key and the command to fix it. Until Phase B lands, the check runs against fixtures only (Task 7) and cannot go red on the siblings' work. So **no sibling plan needs an edit**: their existing "run the suites" step surfaces any drift with an actionable message, and only after their own work has merged.

### Risk this leaves open

If M5a/M5b/M5d slip, Phase B slips with them. That is the intended trade: Phase A delivers the enforceable rule and the whole mechanism on day one, and the only thing gated on the siblings is mechanical text movement. If a decision is later taken to ship M5e before a sibling, Phase B can run over whatever has merged and be re-run afterwards — the extractor in Task 8 is idempotent by construction, precisely so that is cheap.

import { UI_LANGUAGES } from "./settings";

/** `app.uiLanguage` (spec §8): the five shipped locales plus `system`. */
export type UiLanguage = (typeof UI_LANGUAGES)[number];

/** Spec §17 v1 locales: `en` (source), `es`, `ja`, `zh`, `pt`. */
export const LOCALES = ["en", "es", "ja", "zh", "pt"] as const;
export type Locale = (typeof LOCALES)[number];

/** The locale every other one falls back to, key by key (spec §17). */
export const SOURCE_LOCALE: Locale = "en";

export function isLocale(value: unknown): value is Locale {
  return typeof value === "string" && (LOCALES as readonly string[]).includes(value);
}

/**
 * The locale a window opens in (spec §8, §17). `system` reads the OS language; anything we don't ship,
 * and any unreadable value, resolves to `en` -- this runs during window creation, where throwing would
 * cost the user their app rather than their translation.
 *
 * A system locale arrives in several shapes: Intl gives `ja-JP`, POSIX `LANG` gives `es_ES.UTF-8`, and a
 * script subtag gives `zh-Hans-CN`. Only the primary subtag is significant here, because we ship no
 * region- or script-specific variants.
 */
export function resolveLocale(uiLanguage: string, systemLocale: string | undefined): Locale {
  if (isLocale(uiLanguage)) return uiLanguage;
  if (uiLanguage !== "system" || !systemLocale) return SOURCE_LOCALE;
  const [primary] = systemLocale.toLowerCase().split(/[-_.]/);
  return isLocale(primary) ? primary : SOURCE_LOCALE;
}
```

import type { Locale } from "@jslab/shared";

/**
 * The locale a window opens in, carried on the URL (spec §17). The view needs it synchronously, before its
 * first render -- `strings.ts` is imported at module scope by 35 files, long before `app.bootstrap` resolves --
 * and a query parameter is the only channel already present when the bundle's first line runs. It is also why
 * changing the language needs a restart: the URL is fixed when the window is created.
 *
 * `views://` is not a registered scheme for `new URL`, so this edits the query textually rather than round-
 * tripping through URL, and replaces any existing `lng` instead of appending a second one.
 */
export function withLocale(url: string, locale: Locale): string {
  const [base, query = ""] = url.split("?");
  const parameters = query
    .split("&")
    .filter((entry) => entry !== "" && !entry.startsWith("lng="))
    .concat(`lng=${locale}`);
  // A dev-server origin has no path of its own ("http://localhost:5173"); give it the root path so the
  // `${origin}/*` navigation rule matches.
  const path = base?.includes("/", base.indexOf("//") + 2) ? base : `${base}/`;
  return `${path}?${parameters.join("&")}`;
}

```ts
import { readFileSync } from "node:fs";
import { join } from "node:path";
import { type Locale, SOURCE_LOCALE } from "@jslab/shared";

export type Translate = (key: string, vars?: Record<string, string | number>) => string;

export interface TranslatorOptions {
  /** `AppPaths.localesDir`: Resources/app/locales in a packaged build. */
  dir: string;
  locale: Locale;
  /** Injectable for tests; defaults to a UTF-8 readFileSync. */
  read?: (path: string) => string;
}

const PLACEHOLDER = /\{\{(\w+)\}\}/g;

/** Replaces `{{name}}`. An unknown placeholder is left verbatim, so a gap shows up in a bug report. */
export function interpolate(template: string, vars: Record<string, string | number>): string {
  return template.replace(PLACEHOLDER, (match, name: string) =>
    Object.hasOwn(vars, name) ? String(vars[name]) : match,
  );
}

function lookup(table: Record<string, unknown> | null, key: string): string | null {
  if (!table) return null;
  let node: unknown = table;
  for (const segment of key.split(".")) {
    if (typeof node !== "object" || node === null) return null;
    node = (node as Record<string, unknown>)[segment];
  }
  return typeof node === "string" ? node : null;
}

function load(dir: string, locale: Locale, read: (path: string) => string): Record<string, unknown> | null {
  try {
    const parsed: unknown = JSON.parse(read(join(dir, `${locale}.json`)));
    return typeof parsed === "object" && parsed !== null ? (parsed as Record<string, unknown>) : null;
  } catch {
    // A missing or corrupt locale file costs a translation, never the app: this runs while the window and
    // the native menu are being built.
    return null;
  }
}

/**
 * Spec §17's "small `t()` in Main". Reads the same `<lng>.json` files the UI ships (see `AppPaths.localesDir`),
 * falls back to `en` key by key, and returns the key itself when neither locale has it -- a visible mistake
 * rather than an invisible blank menu item.
 *
 * Plurals use the same `_one` / `_other` suffixes i18next does, so one set of locale files serves both sides.
 * Only English plural rules are applied here, which is all Main's seven pluralized strings need; a locale with
 * richer rules supplies `_other` and the UI side (real i18next) handles its own.
 */
export function createTranslator(options: TranslatorOptions): Translate {
  const read = options.read ?? ((path: string) => readFileSync(path, "utf8"));
  const primary = load(options.dir, options.locale, read);
  const fallback = options.locale === SOURCE_LOCALE ? primary : load(options.dir, SOURCE_LOCALE, read);

  return (key, vars = {}) => {
    const candidates =
      typeof vars.count === "number" ? [`${key}_${vars.count === 1 ? "one" : "other"}`, key] : [key];
    for (const table of [primary, fallback]) {
      for (const candidate of candidates) {
        const value = lookup(table, candidate);
        if (value !== null) return interpolate(value, vars);
      }
    }
    return key;
  };
}
```

**How this satisfies "a key check must fail loudly."** Four independent assertions, none of which can pass on an empty or unread input:

1. `enKeys.length` must equal `manifest.length`, and the manifest is a committed file — so any added or removed key is a deliberate, reviewable diff, not a silent drift. **This is the expected-total assertion**: it compares against a real recorded number, so a run that loaded nothing reports `0 !== 464`, a failure.
2. `enKeys.length` must be at least `MIN_KEYS` (464 — the measured count of today's two string modules, before the sweep even adds command titles). A catalogue that collapses cannot read as a pass.
3. `unknownKeys` — a `t("…")` call site with no key in `en` — must be empty. This is the "someone added a string and forgot to regenerate" case.
4. `unusedKeys` — a key in `en` no call site references — must be empty. This is the "someone deleted a control and left its copy behind" case, and it is why the check is bidirectional.

Per-locale, `extra` (a key not in `en`, i.e. a typo or a stale key) fails, and `translated` below the recorded `coverage` number fails. `missing` does **not** fail per-PR: §17 says missing keys fall back to `en`, and Task 12 explains why a hard 100 % gate would force machine-translated filler. `--strict` turns `missing` into a failure for the v1 parity gate.

 */
export const MIN_KEYS = 464;

/** `t("some.key")` and `t(\n  "some.key"\n)`. A dynamic key is deliberately not matched. */
const CALL_SITE = /(?<![\w$.])t\(\s*"([^"\\]+)"/g;

export function flattenKeys(value: unknown, prefix = ""): string[] {
  if (typeof value !== "object" || value === null) return [];
  const keys: string[] = [];
  for (const [name, child] of Object.entries(value as Record<string, unknown>)) {
    const path = prefix ? `${prefix}.${name}` : name;
    if (typeof child === "string") keys.push(path);
    else keys.push(...flattenKeys(child, path));
  }
  return keys.sort();
}

export function collectUsedKeys(sources: readonly SourceFile[]): string[] {
  const found = new Set<string>();
  for (const source of sources) {
    CALL_SITE.lastIndex = 0;
    for (const match of source.text.matchAll(CALL_SITE)) if (match[1]) found.add(match[1]);
  }
  return [...found].sort();
}

const without = (from: readonly string[], other: readonly string[]): string[] => {
  const set = new Set(other);
  return from.filter((key) => !set.has(key));
};

export function checkLocales(input: CheckInput): CheckReport {
  const source = input.locales[SOURCE_LOCALE];
  const enKeys = flattenKeys(source);
  const enValues = new Map<string, string>();
  for (const key of enKeys) enValues.set(key, valueAt(source, key) ?? "");
  const used = collectUsedKeys(input.sources);

  const manifestDrift = {
    added: without(enKeys, input.manifest),
    removed: without(input.manifest, enKeys),
  };
  const unknownKeys = without(used, enKeys);
  const unusedKeys = without(enKeys, used);

  const locales: LocaleReport[] = LOCALES.filter((locale) => locale !== SOURCE_LOCALE).map((locale) => {
    const table = input.locales[locale];
    const keys = flattenKeys(table);
    return {
      locale,
      missing: without(enKeys, keys),
      extra: without(keys, enKeys),
      // A key copied verbatim from English is not a translation; counting it as one would let the coverage
      // gate be satisfied by pasting en.json into ja.json.
      translated: keys.filter((key) => {
        const value = valueAt(table, key);
        return value !== null && value !== enValues.get(key);
      }).length,
      recorded: input.coverage[locale] ?? 0,
    };
  });

  const ok =
    enKeys.length >= MIN_KEYS &&
    enKeys.length === input.manifest.length &&
    manifestDrift.added.length === 0 &&
    manifestDrift.removed.length === 0 &&
    unknownKeys.length === 0 &&
    unusedKeys.length === 0 &&
    locales.every((entry) => entry.extra.length === 0 && entry.translated >= entry.recorded);

  return { enKeys, manifestDrift, unknownKeys, unusedKeys, locales, ok };
}

function valueAt(table: unknown, key: string): string | null {
  let node: unknown = table;
  for (const segment of key.split(".")) {
    if (typeof node !== "object" || node === null) return null;
    node = (node as Record<string, unknown>)[segment];
  }
  return typeof node === "string" ? node : null;
}

# Translating JSLab

JSLab ships in English, Spanish, Japanese, Chinese and Portuguese. This page explains how to correct a
translation or add a language.

## Where the files are

Every user-visible string lives in `apps/ui/src/i18n/locales/<lng>.json`, keyed by a dotted, namespaced path
such as `settings.editor.lineWrap.label`. `en.json` is the source: it is generated from the app's own strings,
and it is the only file you should not edit by hand. The Japanese, Spanish, Chinese and Portuguese files are
written by people.

A key missing from your language falls back to English, so a partial translation is genuinely useful — you do
not have to finish a language before opening a pull request.

## Correcting or adding a translation

1. Find the key in `en.json`.
2. Add or edit the same key in `<lng>.json`, keeping the nesting identical.
3. Keep every `{{placeholder}}` exactly as it appears in English. They are filled in at runtime, and a renamed
   or dropped placeholder shows up as literal `{{name}}` text in the app.
4. Run `bun run i18n:check`. It fails if your file has a key English does not, or if the number of translated
   strings in your language went down.

### Plurals

Keys ending in `_one` and `_other` are plural forms, chosen by a `count` value:

```json
{ "tabsDropped_one": "{{count}} tab was skipped", "tabsDropped_other": "{{count}} tabs were skipped" }
```

Languages that do not distinguish plurals need only `_other`; Japanese and Chinese use that form alone.
Languages with more categories may add `_zero`, `_two`, `_few` or `_many` — i18next selects the right one from
the language's CLDR rules.

## Adding a new language

1. Add its code to `LOCALES` in `packages/shared/src/locale.ts` and to `UI_LANGUAGES` in
   `packages/shared/src/settings.ts`.
2. Create `apps/ui/src/i18n/locales/<lng>.json` and import it in `apps/ui/src/i18n/index.ts`.
3. Add the language's own name to the `settings.options.uiLanguage` group — in its own language, as
   `Español` and `日本語` already are.
4. Add an entry for it to `apps/ui/src/i18n/coverage.json`.
5. Run `bun run i18n:check`.

## Things the app does not translate

- **Theme and font names** (`Graphite`, `Dracula`, `JetBrains Mono`) are proper nouns.
- **Values printed in the output panel** — `undefined`, `null`, `Invalid Date`, `[Object: null prototype]` —
  are JavaScript's own notation. Translating them would make the output disagree with the runtime that produced
  it.
- **Key names** such as `Space`, `Home` and `PgUp` label physical keys, which the UI language does not change.
  This is a known v1 limitation.

## Changing the language

Settings → General → Language. JSLab must be restarted for the change to take effect, and it tells you so.

### The transformation rule, once, for Tasks 8–11

Every conversion in this phase is the same edit:

| Before | After | Key |
|---|---|---|
| `run: "Run"` | `run: t("shell.run")` | the property's dotted path |
| `failed: (m: string) => \`Couldn't format: ${m}\`` | `failed: (message: string) => t("format.failed", { message })` | same path; the template's `${x}` become `{{x}}` in `en.json` |
| `settled: (h: number) => \`… ${h === 1 ? "handle" : "handles"}\`` | `settled: (count: number) => t("shell.runState.settled", { count })` | `…_one` / `…_other` in `en.json` |

Three rules hold throughout, and the key check enforces all three:

1. **The exported shape never changes.** `strings.shell.run` stays a string-valued property read, `strings.format.failed(x)` stays a call. **No call site in the 35 importing files is edited in this phase.** That is what keeps the diff reviewable and what let Phase A ship first.
2. **Evaluation is eager, not lazy.** `t()` is called when `strings.ts` evaluates, not on each read, because `apps/ui/src/i18n/index.ts` initializes i18next synchronously and `strings.ts` imports it — so the catalogue is loaded first. Task 6's test `"is initialized at module scope, before any component renders"` is the guard on that ordering; if it ever fails, this whole phase breaks loudly rather than silently serving keys.
3. **`as const` comes off** both string modules. `t()` returns `string`, so literal types are gone. The two places that relied on the narrow types already cast or widen safely (`strings.settings.fields` is cast to `Record<string, { label: string; help: string }>`; `LANGUAGE_LABELS` / `RUNTIME_LABELS` in `apps/ui/src/shell/labels.ts` are annotated `Record<Language, string>` / `Record<Runtime, string>`, which the widened object still satisfies). Typecheck is the check; do not suppress a failure here without understanding it.

**One deliberate key remap, for spec conformance.** §17's stated convention is `settings.editor.lineWrap.label`. Today those strings live at `strings.settings.fields["editor.lineWrap"].label`. The extractor therefore drops the `fields` segment, so the key is `settings.editor.lineWrap.label` exactly as the spec writes it. The TypeScript path keeps `fields`; only the key changes.

Create `apps/ui/scripts/i18n-extract.ts`:

```ts
import { readFileSync, writeFileSync } from "node:fs";
import { join, resolve } from "node:path";
import { LOCALES, SOURCE_LOCALE } from "@jslab/shared";
import { flattenKeys } from "../src/i18n/check";

const UI_ROOT = join(import.meta.dir, "..");
const I18N_DIR = join(UI_ROOT, "src", "i18n");
const LOCALES_DIR = join(I18N_DIR, "locales");

/** Every string leaf, by dotted path. Function leaves are skipped: they are converted by hand (Task 9). */
export function plainLeaves(value: unknown, prefix = ""): Record<string, string> {
  const out: Record<string, string> = {};
  if (typeof value !== "object" || value === null) return out;
  for (const [name, child] of Object.entries(value as Record<string, unknown>)) {
    const path = prefix ? `${prefix}.${name}` : name;
    if (typeof child === "string") out[path] = child;
    else if (typeof child === "object" && child !== null) Object.assign(out, plainLeaves(child, path));
  }
  return out;
}

/**
 * Spec §17 writes the convention as `settings.editor.lineWrap.label`. The strings module nests those under a
 * `fields` object, so the segment is dropped when the key is formed. Only the key changes; the TypeScript
 * path keeps `fields`.
 */
export function remapSettingsFields(keys: Record<string, string>): Record<string, string> {
  const out: Record<string, string> = {};
  for (const [key, value] of Object.entries(keys)) {
    out[key.startsWith("settings.fields.") ? `settings.${key.slice("settings.fields.".length)}` : key] = value;
  }
  return out;
}

/**
 * Dotted keys -> the nested object `en.json` holds. A key that is both a translation and the parent of
 * another key cannot be represented — JSON and i18next each allow only one — so it is a loud ERROR.
 * Do not "fix" this by letting the last writer win: the naive version replaced the string leaf with `{}`
 * and destroyed that translation with no output at all, which is the worse failure of the two.
 */
export function nest(flat: Record<string, string>): Record<string, unknown> {
  const root: Record<string, unknown> = {};
  for (const key of Object.keys(flat).sort()) {
    const segments = key.split(".");
    let node = root;
    for (const [depth, segment] of segments.slice(0, -1).entries()) {
      const existing = node[segment];
      if (typeof existing === "string") {
        throw new Error(
          `i18n key collision: "${segments.slice(0, depth + 1).join(".")}" is already a translation, ` +
            `so "${key}" cannot nest under it. Rename one of the two.`,
        );
      }
      if (typeof existing !== "object" || existing === null) node[segment] = {};
      node = node[segment] as Record<string, unknown>;
    }
    const leaf = segments[segments.length - 1] as string;
    const existing = node[leaf];
    if (typeof existing === "object" && existing !== null) {
      throw new Error(
        `i18n key collision: "${key}" is already a group of keys, so it cannot also be a translation. ` +
          `Rename one of the two.`,
      );
    }
    node[leaf] = flat[key] as string;
  }
  return root;
}

const readJson = (path: string): Record<string, unknown> =>
  JSON.parse(readFileSync(path, "utf8")) as Record<string, unknown>;
const writeJson = (path: string, value: unknown) =>
  writeFileSync(path, `${JSON.stringify(value, null, 2)}\n`);

const enPath = join(LOCALES_DIR, `${SOURCE_LOCALE}.json`);
const fromIndex = process.argv.indexOf("--from");

if (fromIndex !== -1) {
  // Migration mode (Tasks 8, 10, 11): merge a module that still holds literals into en.json.
  const modulePath = process.argv[fromIndex + 1];
  if (!modulePath || modulePath.startsWith("--")) throw new Error("--from needs a module path");
  // Do NOT write `process.argv[process.argv.indexOf("--namespace") + 1]`. With the flag absent indexOf
  // returns -1, so that reads argv[0] — the absolute path of the bun binary — and the truthiness guard
  // lets it through, prefixing every harvested key with a machine-specific path and committing it into
  // en.json. Step 5 below invokes this with no --namespace, so that fires on first use. Test the flag.
  const namespaceIndex = process.argv.indexOf("--namespace");
  const namespaceValue = namespaceIndex === -1 ? undefined : process.argv[namespaceIndex + 1];
  if (namespaceIndex !== -1 && (!namespaceValue || namespaceValue.startsWith("--"))) {
    throw new Error("--namespace needs a value");
  }
  const namespace = namespaceValue ?? "";
  // Resolve against the working directory. A bare `await import(modulePath)` resolves relative to THIS
  // file, so the documented `--from ./src/strings.ts` (run from apps/ui) would look for
  // apps/ui/scripts/src/strings.ts and die with "Cannot find module './src/strings.ts'".
  const imported = (await import(resolve(process.cwd(), modulePath))) as Record<string, unknown>;
  const source = imported.strings ?? imported.default;
  const leaves = remapSettingsFields(plainLeaves(source, namespace));
  const merged = { ...plainLeaves(readJson(enPath)), ...leaves };
  writeJson(enPath, nest(merged));
  console.log(`i18n: merged ${Object.keys(leaves).length} keys from ${modulePath} into en.json`);
}

// Always regenerate the manifest and the coverage record from what is now on disk.
const en = readJson(enPath);
const enKeys = flattenKeys(en);
writeJson(join(I18N_DIR, "keys.json"), enKeys);

const enFlat = plainLeaves(en);
const coverage: Record<string, number> = {};
for (const locale of LOCALES) {
  if (locale === SOURCE_LOCALE) continue;
  const flat = plainLeaves(readJson(join(LOCALES_DIR, `${locale}.json`)));
  // A string copied verbatim from English is not a translation.
  coverage[locale] = Object.entries(flat).filter(([key, value]) => value !== enFlat[key]).length;
}
writeJson(join(I18N_DIR, "coverage.json"), coverage);
console.log(`i18n: keys.json now records ${enKeys.length} keys`);

#### Where the translated copy actually comes from — read this before writing any JSON

This is the part of the milestone that is not a programming problem, and the plan will not pretend otherwise.

- **`en` is real and complete.** It was extracted mechanically from copy that already shipped and was reviewed in M1–M4. Nothing about it is guessed.
- **`es`, `ja`, `zh` and `pt` need a human.** JSLab's UI copy is dense with terms of art (`Auto Log`, `magic comment`, `logpoint`, `working directory`, `trailing comma`, `loop protection`, `spare`) whose conventional translations differ per language and per developer community. Machine output for those is confidently wrong in ways a non-speaker cannot detect, and shipping ~595 machine-translated strings under a "supported language" label is worse for a Japanese user than falling back to English, because they cannot tell which strings to distrust.
- **This task therefore ships a deliberately small seed**, listed exhaustively below: about 25 keys per language, confined to short, unambiguous, high-traffic chrome where the correct term is not in dispute — menu sections, the seven settings tab names, and the core verbs. Everything else falls back to `en`, which §17 explicitly provides for: *"missing keys fall back to `en`."*
- **The seed values below are drafts and are labelled as such.** They are a starting point for review, not a finished translation. `docs/qa/m5e-checklist.md` carries an explicit unchecked item for native-speaker sign-off on each of the four, and it stays unchecked until a speaker of that language has actually reviewed it. Do not tick it on the strength of this plan.
- **Full coverage is a v1 parity-gate obligation (M6), not an M5e one.** `--strict` exists for that gate. Reaching it requires recruiting four reviewers, which is a project task, not a coding task, and `docs/user/translating.md` is the recruiting surface.

#### Reconciling the two halves of §17

§17 says both *"A CI check verifies every locale has all keys"* and *"missing keys fall back to `en`"*. Taken literally together, the fallback could never fire. The plan resolves it this way, and says so out loud rather than quietly picking one:

| Condition | Per-PR (`bun run i18n:check`) | Parity gate (`--strict`) |
|---|---|---|
| A locale has a key `en` does not (typo, stale key) | **fail** | fail |
| A locale's translated count fell | **fail** | fail |
| `en` drifted from `keys.json` | **fail** | fail |
| A locale is missing keys | report the number | **fail** |

The fallback is real and exercised; the check still cannot go green while a locale contains a key that resolves to nothing.

```ts
import { flattenKeys } from "./check";

export interface WidthViolation {
  key: string;
  width: number;
  budget: number;
}

/**
 * Columns a string occupies in a monospace-ish run: East-Asian Wide and Fullwidth characters take two, and
 * combining marks take none. This is a deterministic proxy, not a measurement -- the unit suite runs under
 * happy-dom, which has no layout engine, so nothing here can measure a rendered label. It bounds the realistic
 * failure (a translation two or three times the English length in a fixed-width control); the subtle ones are
 * caught by the ja/es screenshot pass in docs/qa/m5e-checklist.md.
 */
export function displayWidth(text: string): number {
  let width = 0;
  for (const character of text) {
    const code = character.codePointAt(0) ?? 0;
    if (code >= 0x0300 && code <= 0x036f) continue; // combining diacritics
    width += isWide(code) ? 2 : 1;
  }
  return width;
}

function isWide(code: number): boolean {
  return (
    (code >= 0x1100 && code <= 0x115f) || // Hangul Jamo
    (code >= 0x2e80 && code <= 0x303e) || // CJK radicals, Kangxi, CJK symbols
    (code >= 0x3041 && code <= 0x33ff) || // Hiragana, Katakana, Hangul Compatibility, CJK compatibility
    (code >= 0x3400 && code <= 0x4dbf) || // CJK Extension A
    (code >= 0x4e00 && code <= 0x9fff) || // CJK Unified Ideographs
    (code >= 0xa960 && code <= 0xa97f) ||
    (code >= 0xac00 && code <= 0xd7a3) || // Hangul syllables
    (code >= 0xf900 && code <= 0xfaff) || // CJK compatibility ideographs
    (code >= 0xfe30 && code <= 0xfe4f) ||
    (code >= 0xff00 && code <= 0xff60) || // Fullwidth forms
    (code >= 0xffe0 && code <= 0xffe6) ||
    (code >= 0x20000 && code <= 0x3fffd) // CJK Extension B and beyond
  );
}

/**
 * Columns each width-critical control can hold. Derived from apps/ui/src/styles.css: the native menu bar and
 * its submenus size to content but crowd the macOS menu bar past roughly 14 columns per section; a status-bar
 * item sits in a nowrap row with several siblings; a settings tab label sits in the 760 px window's nav column;
 * `settings.restartRequired` is a badge beside a field label.
 */
export const WIDTH_BUDGETS: Record<string, number> = {
  "menu.file": 14,
  "menu.edit": 14,
  "menu.actions": 14,
  "menu.tools": 14,
  "menu.view._": 14,
  "menu.themes": 14,
  "menu.window": 14,
  "menu.help": 14,
  "menu.runtime": 16,
  "menu.language": 16,
  "menu.layout": 16,
  "settings.tabs.general": 16,
  "settings.tabs.editor": 16,
  "settings.tabs.formatting": 16,
  "settings.tabs.appearance": 16,
  "settings.tabs.npm": 16,
  "settings.tabs.build": 16,
  "settings.tabs.advanced": 16,
  "settings.restartRequired": 22,
  "shell.runtime": 18,
  "shell.language": 18,
  "settings.options.runtime.bun": 26,
  "settings.options.runtime.browser": 26,
  "settings.options.runtime.browser-node": 26,
  "palette.placeholder": 32,
};

/** Only keys this locale actually defines are checked; a missing key falls back to `en`, already in budget. */
export function checkWidths(table: unknown, budgets: Record<string, number>): WidthViolation[] {
  const present = new Set(flattenKeys(table));
  const violations: WidthViolation[] = [];
  for (const [key, budget] of Object.entries(budgets)) {
    if (!present.has(key)) continue;
    const value = valueAt(table, key);
    if (value === null) continue;
    const width = displayWidth(value);
    if (width > budget) violations.push({ key, width, budget });
  }
  return violations.sort((a, b) => a.key.localeCompare(b.key));
}

function valueAt(table: unknown, key: string): string | null {
  let node: unknown = table;
  for (const segment of key.split(".")) {
    if (typeof node !== "object" || node === null) return null;
    node = (node as Record<string, unknown>)[segment];
  }
  return typeof node === "string" ? node : null;
}

import { type LaunchedApp, launchApp, waitFor } from "../src";

afterEach(async () => {
  await app?.dispose();

interface Item {
  label?: string;
  submenu?: Item[];
}

    // launchApp writes settings.json before the app starts, so this is exactly what a user sees after the
    // restart the setting asks for.
