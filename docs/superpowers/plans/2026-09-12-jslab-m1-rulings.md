# JSLab M1: Execution Rulings and Deviations

## 1. Purpose

This document records the decisions, deviations and lessons produced while executing `2026-09-12-jslab-m1-core-scratchpad.md` (the M1 plan) task by task under an execution ledger that has since been deleted per the SDD workflow. It exists so that anything the ledger held which changed the plan's code, its test counts, or the process used to build and verify it survives in the repository in durable, sanitized form. The plan and the design spec (`2026-09-12-jslab-design.md`) remain the binding authority for what JSLab is; this document only explains where and why the as-built code, tests, or process deviated from the plan text, and what was ruled and why during execution.

- Tests: 268 in total — shared 13, rpc-schema 6, ui 56, serializer 27, transform 51, runner-bun 30, desktop 85.

- Both the dev build and the packaged canary build boot correctly, verified by script (process liveness, heartbeat/reload checks, single warm runner, clean teardown).

### 3b. Task-level rulings (unnumbered in the source ledger)

These arose inside individual task review/fix cycles and changed the plan's reference code, its test counts, or both. IDs below are assigned for this record; they were not numbered in the source.

| ID | Decision | Reason | Consequence if wrong |
|---|---|---|---|
| T1-R1 | A plan-mandated expectation (that the root test/typecheck scripts fail cleanly with zero workspace packages) is accepted as a one-time exception for the very first task, with no code change. | No workspace package exists yet at that point in the build-out; the condition the plan worried about cannot occur before any package does. | The single commit at that point would fail CI in isolation, but there was no remote to run CI against. |
| T4-R1 | A serializer ordering defect is fixed by moving the "is this a Proxy" check to the very first branch of object encoding, ahead of every built-in-type check, so a Proxy wrapping a `Date`/`RegExp`/etc. is always flagged as a Proxy instead of triggering its traps. | The design spec requires Proxies to never be unwrapped through their traps during serialization. | None identified; the fix is a pure reordering with an added regression test. |
| T5-R1 | A reserved-identifier check in the source transform is widened from "top-level scope only" to "any scope," so a nested function can't shadow the runtime helper name. | The spec's wording has no scope qualifier; the narrower check let user code silently break the instrumentation. | None identified; covered by an added nested-scope test. |
| T7-R1 | A process handle is released on the child process's `exit` or `close` event (not only `exit`), made idempotent, so a spawn failure that never fires `exit` doesn't leak a handle. | A failed spawn (e.g., a missing binary) only fires `error`/`close`, and the original code only released on `exit`. | An edge case where `error` fires on a still-running child could under-count a handle. |
| T7-R2 | Superseding T7-R1: handle release moves to `exit` **and** `close`, with **no** listener on `error` at all. | A listener on `error` was found to suppress the runtime's own default "unhandled" behavior, silently hiding spawn failures from user code that had no error handler of its own. | If some spawn-failure mode fires neither `exit` nor `close`, that handle would still leak. |
| T8-R1 | Once a run's state is "stopped," no further error events are emitted for it; the guard lives at the single point where all error paths converge. | The user asked the run to stop; errors produced purely by the ensuing teardown are noise, not information. | A genuine error thrown in the narrow window between Stop and process teardown would not be shown. |
| T8-R2 | The runner process now exits promptly when it detects its parent's IPC channel disconnecting (rather than persisting indefinitely). | A controlled probe confirmed that without this, a crash of the main process leaves every runner and its user-code timers running forever, reparented to the OS. | None identified; verified by a dedicated regression test with no leftover processes. |
| T8-R3 | Two related fixes affecting the same file are covered by a single combined review pass instead of two separate ones. | Both changes touch the same startup/lifecycle code, so reviewing them together catches any interaction the isolated reviews would miss. | A defect introduced by the first change could in theory surface one review cycle later than usual. |
| T9-R1 | Five reproduced run-lifecycle defects (a stop that races the runner assignment and never actually kills anything; a superseded run's cleanup deleting a newer run's output; an unhandled promise rejection when a run's internal work fails; a spare-runner pool leaking a runner after being disposed mid-preparation; and a recovery path always showing a "still running" spinner even when nothing is running) are all fixed together, each with its own regression test using dependency-injection points rather than timing hacks. | All five are genuine, user-visible lifecycle bugs (code that keeps running after Stop, false "still busy" states, runs failing unpredictably, leaked processes, a stuck spinner) discovered by an independent reviewer's own reproduction scripts. | The plan's original reference code for this area is now stale; recorded here rather than rewriting the plan text after the fact. |
| T9-R2 | Fixing the five T9-R1 defects also increases downstream test counts for every task that builds on this code; the plan document itself is not retroactively edited to reflect the new counts — this ledger (and now this record) is the source of truth for the deviation. | Editing a large, already-reviewed plan document mid-execution is more error-prone than tracking the delta separately. | The plan's cumulative test-count text diverges from the as-built counts; anyone consulting the plan for counts must consult this record instead. |
| T9-R3 | A follow-up defect in the spare-runner pool (a runner still gets pre-warmed for a tab that was invalidated mid-request, leaking a long-lived process) is fixed by capturing a generation marker at the start of the request and skipping the pre-warm step if that generation changed during the request, rather than removing the retry-on-invalidate behavior entirely. | Retrying on invalidation legitimately serves the case where a still-current run needs a freshly configured runner; only the trailing pre-warm step needed the extra guard. | After a configuration-driven invalidation mid-request, the next run on that tab starts without a pre-warmed spare (a small performance cost, not a correctness one). |
| T10-R1 | Three worker-lifecycle defects in the transform host (a worker that exits without an error event hangs every pending and future transform request forever; calling transform after the host was disposed hangs forever; and a cache-eviction race can delete a newer cache entry under an old key) are all fixed together: exit/close now rejects pending work and forces a fresh worker on the next call; a disposed flag makes later calls reject immediately; and cache cleanup only deletes an entry if it's still the same cached promise. | All three were reproduced independently and each represents a real hang or data-loss path in normal use. | None identified; each ships with its own regression test. |
| T11-R1 | The debounced file-writer used by the settings/session stores is changed so that one failed write no longer poisons every future write attempt; a `flush()` call rejects only for its own write, not a stale earlier failure; and background (non-`flush`-triggered) write failures are routed to an injectable error callback instead of becoming an unhandled promise rejection. | An independent reviewer's reproduction showed that after one write failure, later saves were silently and permanently dropped, and a background failure crashed the reproduction process outright. | None identified after two fix rounds; each sub-case ships with its own regression test. |
| T11-R2 | The atomic-write helper now cleans up its temporary file on any failure (not only a rename failure), and preserves an existing file's permission bits when no explicit mode is given (an explicit mode still wins). | Without these, a failed write could leave a stray temp file behind, and a routine re-save could silently loosen a file's permissions (e.g., from owner-only back to the default). | None identified; both ship with regression tests. |
| T11-R3 | A follow-up fix makes `flush()` resolve (not reject) when there is nothing currently pending to write, even if an earlier background write had failed. | Without this, one transient background write failure meant every future shutdown-time `flush()` call threw forever, even though the failure had already been reported through the error callback. | A caller that flushes with nothing pending won't separately learn that an earlier write failed — but it was already told, once, via the error callback. |
| T12-R1 | The recovery path in both the settings and session stores now writes the recovered data back **without** creating a fresh backup copy (a normal, non-recovery save still makes one). | Making a backup copy during recovery would overwrite the still-good backup with the same corrupt-then-recovered data, defeating the safety net a second corruption would need. | None identified; a normal save still refreshes the backup as before. |
| T12-R2 | A previously fire-and-forget internal update to a tab's contents now has a failure handler that logs the error, instead of letting a failed background write disappear as an unhandled rejection. | An independent reviewer showed that a failed buffer flush during, e.g., a language rename silently dropped the update with no diagnostic trail. | None identified; covered by a regression test. |
| T12-R3 | The helper that shells out to read a keyboard-modifier state now kills its own subprocess if a timeout elapses, instead of only abandoning the promise. | Without this, a hung subprocess call would leave an orphaned process behind indefinitely. | None identified; verified by direct inspection and a live low-timeout re-check. |
| T14-R1 | The main-process startup watchdog now uses a longer "boot grace" deadline before the very first UI heartbeat arrives, and a shorter steady-state deadline afterward; a reload never resets whether the first heartbeat has already been seen. | The original flat, short deadline would reload a real UI window forever if its first paint legitimately took longer than that deadline (e.g., a cold start). | None identified; covered by unit tests for both deadline phases. |
| T14-R2 | The entire startup sequence is now wrapped so that any rejection during it is logged, shown to the user via a native message box where the toolchain supports one, and then quits cleanly, instead of letting the app "just not launch" with no diagnostic. | A store-open failure during a recovery rewrite could previously crash startup before any window ever appeared, with nothing visible to the user. | None identified; this path is inherently tied to the native runtime and is not independently unit-testable. |
| T14-R3 | A comment describing an ambient type declaration's scope is corrected (no code change): the declaration is program-wide, not file-scoped as originally written. | Documentation accuracy only; the actual behavior was already correct because the UI code lives under a separate compiler program in this milestone. | None; flagged for a later milestone to revisit if that separation ever changes. |
| T15-R1 | A settings-driven auto-run debounce timer now re-checks whether auto-run is still allowed at the moment it actually fires (not only when it was first scheduled), and cancels a pending timer outright when auto-run becomes disallowed mid-wait. | Without this, a debounce timer scheduled just before Safe Mode activates, or before Auto Run is turned off, would still fire once the wait period ended. | None identified; covered by regression tests for both trigger paths. |

## 4. Deviations from the plan's code as built

Grouped by package/app. Each item names the change, why, and which task/fix round produced it.

### shared

- Added `DEFAULT_RUNTIME` (`browser-node`) and `DEFAULT_LANGUAGE` (`typescript`) as exported constants, used by the settings schema and by new-tab creation, replacing an inline default that had drifted from the spec's stated default. Final fix wave (M13), reconciled with a settings-schema test update.

### rpc-schema

- `tabId` values are now validated against a strict safe-id regex (alphanumeric plus underscore/hyphen, bounded length) everywhere a tab id crosses the RPC boundary (run start/stop/kill/wait, expand, buffer-changed, tab-patch), rejecting path-traversal-shaped or otherwise unsafe strings. Final fix wave (M1 tabId item), T7 fix round context.

### serializer

- Proxy-order fix: the "is this a Proxy" check now runs before any built-in-type check in object encoding, so a Proxy wrapping a `Date`/`RegExp`/etc. is always flagged as a Proxy rather than triggering its traps. T4 fix round 1.
- Added a per-event/per-call encoding size budget (256 KB by default, unbounded during expand), with an internal "oversized" fallback that returns a handle/preview instead of the full value once the budget is exhausted. Final fix wave (I2).
- Fixed a defect in the new budget logic where an internal "budget exceeded" sentinel could escape into user-visible `console.log` output once the budget was already exhausted; the budget-check state is now reset before computing an oversized-value fallback, and a stray sentinel is mapped to a safe placeholder string as defense in depth. Final fix wave round 2 (N1).

### transform

- Reserved-identifier (`__jl`) detection now scans every scope, not only the top level, closing a gap where a nested-function binding of that name silently broke the runtime helper instead of producing a diagnostic. T5 fix round 1.

### runner-bun

- Process-handle release timing changed twice: first from "on exit only" to "on exit or close," then to "on exit and close, with no listener on `error`," because a listener on `error` suppressed the runtime's own default unhandled-error behavior for spawn failures. T7, two fix rounds.
- The runner process now exits when it detects its parent's IPC channel disconnecting, closing an orphaned-process gap confirmed by a direct probe. T8 fix round 2.
- Error events are suppressed for a run once its state is "stopped," at the single chokepoint where all error-reporting paths converge, so teardown noise isn't shown to the user. T8 fix round 1.
- The event buffer now flushes early on a count or byte-size threshold (200 events / 256 KB) in addition to its existing timer, and closes permanently (dropping further pushes) once a run is stopped, so no output crosses the boundary after Stop. Final fix wave (I1, I2).
- A `WebSocket` global is now wrapped as a tracked handle (constructed, released on close/error), matching the design spec's list of trackable handle types. Final fix wave (I1).
- Console encoding and the runner's own event pipeline now drop output after a run has stopped, in addition to the event-buffer close above. Final fix wave (I1).

### desktop — main process (runs, transform, persistence, services, rpc, app shell)

- The worker-based transform host (wrapped in a caching layer) is wired as the production default; the simpler in-process host is kept only as a fallback class, never the default. R-M1-6.
- Five run-lifecycle defects fixed together in the run coordinator: a stop that raced runner assignment and never killed anything; a superseded run's cleanup deleting a newer run's output entry; an unhandled rejection when the coordinator's internal execution step failed; a spare-runner pool leaking a runner disposed mid-preparation; and a recovery path always reporting "still running" even from a settled state. T9 fix round 1, refined in round 2 with a generation-marker guard on the pool's pre-warm step (T9-R3).
- The transform-host worker wrapper now guards against acting on a stale worker's late `error`/`close` events after it has already been replaced, and rejects immediately once disposed instead of hanging forever. T10 fix round 1, plus one more stale-worker guard in the final fix wave.

## 5. Environment and process lessons

- **Toolchain pinning.** The packaging toolchain was installed once, at a fixed version, at the very start of the milestone, and was never upgraded during execution — an explicit rule enforced throughout, because an in-place upgrade could silently change generated output (tsconfig shape, build scripts) mid-milestone with no way to bisect the cause.
- **`PATH` prefix, not profile edits.** Automated worker shells did not inherit the toolchain's `bin` directory on `PATH` the way an interactive login shell would, even though the user's shell profile already declared it. The fix was a per-command `PATH` prefix on every command that needed the toolchain, never an edit to the shell profile itself.
- **Shell-profile checksum guards.** Before any operation that could touch a shell profile (installing or syncing the toolchain), a SHA-256 checksum of each profile file was recorded, and re-checked after the operation completed; an unexpected change would have stopped execution rather than being silently accepted. This caught nothing going wrong, but was maintained throughout as a safety net around tooling that is known to sometimes touch shell configuration.
- **zsh word-splitting and PID arrays.** An early process-teardown attempt used an unquoted shell variable holding a space-separated list of PIDs as arguments to `kill`; zsh does not word-split unquoted variables the way other shells do, so the command received one malformed argument instead of several PIDs, failed silently, and left processes running. The fix, applied everywhere thereafter: always capture PIDs into a shell array and iterate one PID per `kill` call, and never suppress a `kill` command's errors without immediately re-checking whether the target process actually died.
- **Internal-disk working directory for launches (the TCC removable-volume hang).** The single biggest debugging investment of the milestone: a scripted, backgrounded launch of the packaged app hung indefinitely with no error. Root cause: the runtime opens its own current working directory during startup, and when that directory lives on a removable or external volume, the operating system raises a hidden permission consent prompt — which a backgrounded process with no interactive session can never display, so the underlying file operation blocks forever. A normal double-click launch is never affected, because it always starts with a working directory on the internal disk. The fix, generalized into a standing rule: every scripted or automated launch of the app must first change its own working directory to somewhere on internal disk before executing the launcher.
- **Scoped, per-PID teardown.** Process teardown for both the app and its build tooling used a read-only process lookup scoped strictly to paths that are provably owned by this project (its own build output directory, its own application-data directory) — never a broad match on a process name — followed by a `SIGTERM`, a wait, and a `SIGKILL` only for genuine survivors, each verified against a final process sweep. This avoided any risk of killing an unrelated process that happened to share a name.
- **No screenshots, no synthetic keystrokes.** Screen captures, where taken at all, were always window-scoped, never full-screen (following an earlier incident where a full-screen capture exposed unrelated on-screen content). Simulating keyboard input or clicks via OS-level automation was ruled out entirely, because it can trigger a macOS Accessibility permission prompt with no way for an unattended process to answer it; any check that genuinely needs typing, clicking, or a keyboard shortcut was left for a human and marked pending rather than faked or skipped silently.
- **Clean-room rule.** Throughout the milestone, and explicitly repeated to every research-oriented worker dispatched, the reference commercial product this project takes inspiration from was never unpacked, decompiled, or read at the binary level — only its publicly documented behavior was used as a comparison point.
